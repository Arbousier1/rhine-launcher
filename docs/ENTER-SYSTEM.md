# ENTER SYSTEM 首次点击停顿修复

## 根因

旧版本在资源加载时只编译主场景材质，没有实际准备完整绘制管线。点击 ENTER SYSTEM 后首次运行阴影、法线/深度、AO、景深及材质过渡分支，主线程在 getProgramInfoLog / getUniforms 中同步等待着色器链接，出现约 1.2–1.37 秒的停顿。同像素大小的逻辑布局切换还可能重新分配刚准备好的目标缓冲。

## 改动

- 按最终画质、最终像素尺寸准备实际合成管线，覆盖材质低/中/高过渡状态、阴影和后处理，并等待真实 GPU fence 完成。
- 准备期间不推进镜头、时间或波浪。暂用单个实例练习相同的实例化程序，随后恢复所有可见性、裁剪、实例数量及材质参数；实际画面没有减少模型或降采样。
- 清理隐藏的准备画面，只有资源真正准备完成才让入口按钮进入可用状态，没有在点击后增加固定延时或额外淡出遮罩。
- 按实际整数像素尺寸缓存渲染目标，避免逻辑舞台变化或浮点尾差造成重复分配。
- 等待有取消、超时与状态恢复。准备中离开页面不会留下轮询或画布。

## 验证

同一程序、相同 1600×900、DPR 1、原始画质，保存旧构建资源进行真实鼠标点击对照。

- [旧构建复测](../.reference/enter-control-repeat.json)：首 3 秒 UI 帧间隔最大约 1375 ms；记录到 8 个超过 50 ms 的主线程长任务，调用栈集中在着色器链接。
- [修复复测](../.reference/enter-fixed-repeat.json)：上述着色器链接长任务为 0，点击窗口没有主线程长任务；UI 帧耗时 P95 为 12.5 ms。
- [最终复测](../.reference/enter-fixed-final.json)：同样没有主线程长任务。不同轮次的帧间隔仍受 GPU 负载及分析器影响，因此不宣称固定 GPU FPS，也不挑选最大帧间隔当成纯 CPU 指标。
- [生命周期验证](../.reference/enter-lifecycle.json)：正常完整入场到解密完成；三次真实 REINITIALIZE → ENTER SYSTEM 均无主线程长任务、始终只有一个画布；在 GPU 准备中离开页面后没有残留画布或浏览器错误。
- [最终回归](../.reference/enter-final-regression.json)：55 个测试文件，884 项通过、1 项可选联网测试跳过、0 失败；类型检查和两套生产构建通过。

可复查脚本：[点击分析](../.reference/enter-profile.mjs)、[生命周期](../.reference/enter-lifecycle.mjs)。最初分析器启动开销不计入复测点击窗口。

首次连接现在会先完成必要 GPU 准备；这是实际初始化，不是人为增加等待。原始 GLB、默认画质、相机曲线、波浪、抽取与归位效果保持不变。
